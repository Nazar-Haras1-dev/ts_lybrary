# Лабораторна робота №2: відповіді на контрольні питання

1. У великому застосунку TS ловить помилки типів до запуску, дає надійне автодоповнення й рефакторинг (перейменування по всьому проєкту), робить контракти між модулями явними (інтерфейси), а код самодокументованим. Це знижує кількість помилок і спрощує роботу в команді.
2. **Інтерфейс** описує лише форму (контракт) і зникає після компіляції; **клас** містить реалізацію й створює об'єкти. Інтерфейс варто брати, коли потрібен лише контракт: наприклад, `IBook` описує дані книги, а `Book` реалізує їх із логікою. Через інтерфейс (`Identifiable`) `Library<T>` приймає будь-які об'єкти з `id`.
3. **Generics** — типи-параметри (`Library<T>`), що дозволяють написати код один раз для різних типів зі збереженням типобезпеки. Один `Library<T>` керує і `Book`, і `User`; `findById` повертає саме `Book | undefined`. Без generic довелося б або дублювати клас для кожного типу, або використовувати `any` і втратити перевірку типів.
4. **ES-модулі** — файли з `import`/`export` (кожен файл має власну область видимості, залежності явні). **Namespace** — іменований контейнер усередині коду (`namespace Validation {}`) для групування функцій. Namespace в модулі доречний для логічного групування споріднених функцій під одним ім'ям, як `Validation.validateBook(...)`.
5. **models** — дані та типи (`Book`, `User`, інтерфейси), нічого не знають про UI чи storage. **services** — бізнес-логіка і стан (`Library<T>`, `LendingService`, `Storage`, `NotificationService`), без DOM. **utils** — чисті допоміжні функції (валідація, генерація id, пагінація). **ui** — єдиний шар, що працює з DOM.
6. Клас `Storage` обгортає `localStorage`: `save` робить `JSON.stringify` і `setItem`, `load` читає `getItem` і `JSON.parse` (з fallback при помилці), `remove` і `clear` видаляють дані. При запуску `index.ts` читає списки й відновлює об'єкти через `Book.fromJSON`. Обмеження LocalStorage: ~5 МБ, лише рядки, синхронний (блокує потік), немає шифрування, доступний будь-якому скрипту на сторінці, прив'язаний до браузера й домену.
7. `LendingService.borrow(bookId, userId)` перевіряє, що книга та користувач існують, книга вільна й у користувача менше 3 книг; потім `book.borrow(userId)` записує `borrowedBy = userId`. `giveBack(bookId)` скидає `borrowedBy` у `null`. Стан зберігається, а UI перемальовується: у позиченої книги замість синьої «Позичити» жовта кнопка «Повернути».
8. Валідація живе в `Validation` (namespace). Обов'язкові поля — `trim().length > 0`; id — `/^\d+$/`; рік — `/^(1\d{3}|20\d{2})$/` плюс перевірка «не пізніше поточного року». Регулярка пропускає 1000–1999 і 2000–2099, відсікає літери, дробові значення та числа іншої довжини. Помилки виводяться червоним текстом під полем.
9. Один користувач може позичити максимум **3** книги (`MAX_BORROWED`). При спробі взяти четверту `LendingService` повертає результат з `ok: false` і поясненням, а `NotificationService` через підписку UI відкриває модальне вікно з цим повідомленням.
10. Вимога змушує вчитися будувати UI програмно: розмітка стає залежною від стану, компонентами можна перевикористовувати (функції `createForm`, `renderList`). DOM будується через `document.createElement` (хелпер `h`), збирається в дерево й монтується в `<div id="app">`; оновлення — `replaceChildren`.
11. `webpack.config.js` описує збірку. Ключові налаштування: `entry` (`src/index.ts`), `output` (`dist/bundle.js`), `module.rules` (`ts-loader` для `.ts`, `sass-loader` + `css-loader` + `style-loader` для стилів), `plugins` (`HtmlWebpackPlugin` вставляє скрипт в HTML), `devServer` (порт 9000, HMR), `resolve.extensions`.
12. **ESLint** аналізує якість і помилки коду (невикористані змінні, `any`, потенційні баги). **Prettier** лише форматує (відступи, лапки, крапки з комою) і не шукає помилок. `eslint-config-prettier` вимикає правила ESLint, що конфліктують із Prettier.
13. Юніт-тести перевіряють методи ізольовано. `Library`: додавання, відмова на дубль id, видалення, пошук. `Validation`: обов'язкові поля, id, рік. Приклад:
    ```ts
    it('видаляє існуючий елемент', () => {
      expect(lib.remove('1')).to.equal(true);
      expect(lib.size).to.equal(0);
    });
    ```
14. **Husky** встановлює Git-хук `pre-commit`, який запускає `npm run lint` і `npm test` перед кожним комітом; якщо будь-яка команда впала, коміт блокується. Він вирішує проблему «зламаного коду в репозиторії»: усі в команді проходять однакові перевірки.
15. *(Заповни цифрами зі своїх вимірів, див. README.)* Зазвичай: Vite стартує dev-сервер практично миттєво (нативні ES-модулі + esbuild), webpack спочатку збирає весь бандл. Конфіг Vite коротший (TS і CSS працюють «з коробки»), у webpack потрібні loaders і plugins. Продакшн-збірка обох подібна за розміром; Vite (Rollup) зазвичай швидший.
